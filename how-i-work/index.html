How I work with AI

AI agents are fast at producing code and unreliable at judging it. So I built a workflow where the agents do the implementation and every decision that matters goes through me: what we build, how it's designed, how we'll know it works, and what gets merged. The workflow is defined and written down, but it isn't finished: AI tooling moves fast, so I keep refining it.

The tools

  • Claude Code (Anthropic) is the main agent. The session I talk to plans, runs the checks and writes routine work itself. On high-risk work a separate agent writes the code and the tests from the approved plan. Smaller, cheaper models handle search and lookups.
  • Codex CLI (OpenAI) is a second opinion from a different provider, and read-only. On high-risk work it critiques the spec and the plan; on changes touching login, permissions, money or personal data, the final diff too. It runs only on projects where I've allowed code to go to a second provider.
  • Zed is where I read and review the code.
  • GitHub holds every change as a small pull request.

All of it lives in one versioned repository. The files are the live setup: change one and the next session behaves differently.

Who does what

Each party has one job, and only one of them decides.

  • Me decides

    What we build and what's out; every plan; product, taste, security and privacy calls; and the final merge.

  • Claude Code writes

    Plans, runs the checks and shows the real output. It writes routine work itself; on high-risk work a separate agent writes the code and the tests from the approved plan.

  • Codex reviews risky work

    From a different provider and read-only, it critiques the spec and the plan on high-risk work, and the final diff on login, permissions, money or personal data. Only where I've allowed it.

  1. Classify it out loud. A one-line fix, a routine feature and a change touching login, money or personal data each get a different amount of process.
  2. Plan, then wait for my "go". The plan states what's in, what's out, how we'll know it works, and every blocking assumption as a question. No code before I approve it.
  3. Tests first. A failing test, then the code that makes it pass.
  4. Review in proportion to risk. Routine work gets an automated code review. High-risk work also gets a security threat model, a written spec and, where I've allowed it, Codex's critique.
  5. Prove it. "Done" means real test output, not a claim that it passed.
  6. One small PR per concern, each in its own isolated copy of the repository, so parallel sessions never collide.

Process sized by risk

Process costs time, so it scales with what a change can break. A one-line fix doesn't get a threat model; a change touching login, money or personal data doesn't skip one.

Guardrails

Much of the know-how is packaged as skills: instructions the agent loads for a specific job, like a security audit, a UI review or test-driven development.

Some checks are triggered by what the change is, not by anyone remembering to ask:

  • A security audit in a clean context. It sees the change and its plan, never the conversation that produced them, so it judges the code, not the reasoning behind it. A critical finding is reported first and stops the work until it's fixed or I record an override.
  • Data checks. A migration gets a migration-safety review; a schema or constraint change, a data-integrity review.
  • Observability. A new endpoint, background job or integration gets its logging and error tracking written with it.

What stays mine: approving plans, product and taste calls, anything touching security or privacy, and the final merge. When in doubt, the agent stops and asks.

A setup that keeps changing

None of this is fixed. AI tools change month to month, so I treat the setup like code: versioned, changed in small reviewed steps, each with a reason. The reasons come from what my own sessions show, from periodic audits of the setup itself, and from practices the wider community has tested, which I adopt when they earn their place.

Every review step logs what it found and how much of it I accepted. Usage audits read real sessions to show what each step costs in tokens and time. Together they show which checks pay for themselves, and the process changes when one doesn't: the routine code review now reports at most five findings, after too many of its findings were being rejected.

Measurement also stops changes: a proposed rule for skipping Codex's review was dropped when a test against past reviews showed it would have skipped one that found blocking problems.

The setup also teaches me. For stacks I'm still learning, like TypeScript and Node.js, each plan lists the concepts the work will use, each pull request adds them to a backlog, and a weekly study session I run myself works through it.

Principles

  • Plan before code. Most of the alignment with the AI happens at the plan, not the diff.
  • Small diffs. A change too big to review properly doesn't get merged.
  • Security is never skipped for looking small.
  • Two providers, not one. The model that wrote the code doesn't get the last word on it.
